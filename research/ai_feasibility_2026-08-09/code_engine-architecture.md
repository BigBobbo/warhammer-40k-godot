# code:engine-architecture

## Narrative

## Architecture verdict in one line

The current AI is a pure feed-forward, construct-then-commit heuristic controller: every decision is a closed-form score over analytically-estimated dice outcomes, coordinated across phases by shared plan dictionaries, with zero forward simulation of any kind — and the engine underneath it has no (state, action) -> state' kernel that a search algorithm could call.

## Q1: Decision architecture

`decide()` (40k/scripts/AIDecisionMaker.gd:2197) is a phase switch (2347-2378) into per-phase deciders, each of which ranks concrete candidates with weighted-heuristic scores. There is no lookahead anywhere. The project's own planning doc states it flatly: "The AI is greedy today: it never simulates an opponent reply or an action sequence — no search tree, no state cloning, no what-if evaluation exists anywhere in the file, and the `use_look_ahead()` difficulty gate is dead config that nothing calls" (.llm/ai-overhaul-todo.md:1115-1118). I verified this independently: `use_look_ahead`/`use_trade_analysis` appear only in their own definition file (grep across repo); the only "simulate" in 23,462 lines is a unit-dict duplicate to compute leader-attachment stat multipliers (3367-3377). Dice are handled analytically, never sampled: `_charge_success_probability` enumerates the 36 2D6 outcomes (14399-14418); `_estimate_weapon_damage` chains hit/wound/save probabilities into a scalar expectation (13780-13813).

Cross-phase coordination is real but shallow. `_build_phase_plan` (2794) runs once at the start of the movement phase (5897-5900) and produces: `charge_intent` (any enemy within centroid distance M+12"+ER, scored as melee_dmg*2 plus a lock-dangerous-shooter bonus, 2860-2916), `lock_targets` (enemies ranked by `_estimate_unit_ranged_strength`, 2811-2826), and `shooting_lanes` (pure range circles, no LoS check, 2938-2952). Consumers: objective assignment adds a charge-lane alignment bonus (8225-8241) and a shooting-lane bonus (8243-8256); the shooting phase multiplies down target value for planned charge targets (12878-12882). Movement also clamps moves to keep weapon range (`_clamp_move_for_weapon_range`, 10402) and has hold-for-shooting / heavy-weapon checks (10045, 9758). But the actual focus-fire allocation is built later, in the shooting phase, from post-move positions (12194, 12767) — movement never sees what shooting will really do; it sees a range-circle sketch. Coordination is feed-forward via static class-level dicts, and the movement plan is a per-phase commitment consumed unit-by-unit (`_turn_movement_plan`, 5966-6030) with narrated re-plans.

Reactive windows exist and are answered: AIPlayer connects ~20 phase signals (40k/autoloads/AIPlayer.gd:879-1019) — fire overwatch, heroic intervention, rapid ingress, counter-offensive, command re-roll, epic challenge, tank shock — each with its own closed-form evaluator (e.g. `evaluate_fire_overwatch` 21775, `evaluate_command_reroll_charge` 22370). Unhandled windows are generically declined (AIPlayer.gd:1999-2011).

## Q2: Action space

Movement destinations are constructed, not enumerated. The macro layer (`_assign_units_to_objectives`, 7950) is a greedy global assignment over (unit x objective/screen/corridor-block/attack) pairs with OC bookkeeping, projected enemy OC (7962-7985), and incoming-OC from units already moved (7994-8029). The chosen target position then feeds `_compute_movement_toward_target` (10298): a straight vector toward the target, a 10-angle sweep (±15° to ±75°) only when terrain penalty exceeds 1" (10355-10384), a threat-based safer-position adjustment (10412-10416), then a fraction ladder [1.0, 0.75, 0.5, 0.25, 0.15, 0.1] with per-model collision repair (10447-10500). So effectively one destination per unit with local repair — not K scored candidates over the reachable disc. This mechanically explains the lab's finding that ~50% of moves are farther and lower-scoring than an alternative (reported, background): no alternative is ever scored at the destination level. The config knob that gestures at candidate search (`get_movement_iterations`, AIDifficultyConfig.gd:86) is dead — nothing calls it.

Deployment (`_decide_deployment`, 3912) deploys the *first* undeployed unit (3923-3925 — deployment order is not a decision), at a position from a deterministic formula: column index = deployed_count % (3..5 columns), depth row stagger (3999-4020), blended 70/30 with the nearest in-zone-clamped objective (4022-4025), then a counter-deployment nudge (4028, NORMAL+), a terrain nudge keyed on a role classifier (4035), and AAO spacing. The "ring of 5 alternates" at 4049-4083 is telemetry only — it records what the pick beat, it does not change the pick. Decisions per routed action: measured 380 actions for a full 9-unit-per-side game (.llm/ai-overhaul-todo.md:622); ~800 on larger fixtures (background). MAX_ACTIONS_PER_PHASE = 200 is a deadlock cap (AIPlayer.gd:37).

## Q3: What it structurally knows

Knows (coarsely): per-enemy threat circles — charge threat M+12"+ER, shoot threat = max weapon range, weighted by an abstract 0.3-3.0 danger value (23037-23074), depth-scaled penalties with character/fragile multipliers (23136-23222) — but no LoS in threat eval and no expected-damage-to-me number. Mission math is the strongest area: primary awareness (17863), per-objective VP estimation (17943), mission achievability (18034), ~20 per-secondary `_assess_*` evaluators (18180-18729). Screening is implemented and always on: deep-strike denial (10825), screen positions for value units (10924), corridor blocking (10988), denial radius derived from enemy ingress ability text (22794). Trading is partial: points-per-wound (13122), `_get_trade_efficiency` (13137), VP-diff tempo modifier (13149). Does NOT know: expected enemy shooting damage into a candidate position next turn (incoming-damage estimates exist only for engaged melee, 9265/9288, and overwatch when charging, 14816); anything about the opponent's likely replies.

## Q4: Known weak spots

The code itself carries almost no TODO/FIXME (a case-insensitive grep matched only the word "Shackle"). Self-knowledge lives in .llm/ and docs/: dead difficulty config including the false marketing string "Competitive: Full look-ahead planning" (AIDifficultyConfig.gd:10 vs the dead gates at :37,45,49,53,59,63,86); 92 catalogued damage-math divergences — 17 melee pairs where `_estimate_melee_damage` ignores ANTI-X/TWIN-LINKED/LETHAL HITS entirely, 75 ranged pairs over-predicting 1.5-2.4x with cause not isolated (.llm/ai-overhaul-todo.md:1172-1184); heuristic movement order letting screens move after the screened unit (todo:1081-1093); transports and cargo planning independently (todo:1096-1109); no deployment posture concept and a role classifier that deploys Stormboyz as "durable shooters" (todo:1060-1072, docs/AI_REVIEW_2026-07-11.md:240-244); aircraft burning activations on rejected moves every round (AI_REVIEW:236-239); Kunnin' Infiltrator auto-declined because the AI has no placement pathway (AIDecisionMaker.gd:5809-5819).

## Q5: Compute budget

115 ms/action is measured (380 actions ≈ 44 s of AI compute after ~15 s fixed process overhead; .llm/ai-overhaul-todo.md:631-649). Pacing is proven NOT the cost: time_scale 6→120 moved wall clock <10% (todo:622-626). What dominates inside the 115 ms is explicitly NOT profiled — the focus-fire matrix is "a suspicion, not a finding" (todo:646-649, ai-overhaul-progress.md:266). The figure includes a full `GameState.create_snapshot(false)` deep copy per decision (AIPlayer.gd:1926) plus decide() plus engine application. A 1-5 s human-game budget is 8-40x headroom — enough to score dozens-to-hundreds of movement candidates with the existing scorers (my inference), but not enough for statistical rollouts through the current loop (below).

## Q6: Engine/UI coupling

There is no fast-forward API. Phases are Nodes whose "snapshot" is a live property view over the GameState singleton — by design (ISS-024, 40k/phases/BasePhase.gd:14-24). Actions route through NetworkIntegration → PhaseManager → phase Node, with 43 signal emissions in MovementPhase alone. Even "headless" benchmarking stands up the full battle scene (AIBenchmarkRunner.gd:57-60 "reuses ... the live battle scene"); whole-loop throughput is ~6.5-8.7 actions/sec. The rollout-friendly island is RulesEngine: 16,243 lines of static functions over a plain `board` Dictionary with injected seeded RNG (`resolve_shoot(action, board, rng)` at RulesEngine.gd:749, staged variants 833-1157) — combat resolution is callable headless today. But legality, sequencing, scoring, and stratagem windows live in ~37k lines of phase Nodes (MovementPhase 9,187 lines; ShootingPhase 8,132; FightPhase 6,244). Rollout search therefore requires either extracting a pure kernel from that layer, or save/patch/restore of the global singleton inside the live scene with ~20 connected signals as a re-entrancy hazard. I did not measure a stripped kernel's speed; nobody has.

## Difficulty

Not primarily noise injection. EASY = uniformly random valid actions (2279, 2493). Above EASY, difficulty is: score noise ±1.5/±0.5/0 applied at only four call sites (movement execution order 6160-6161, charge scores 14245/14574, fight order 16391); a charge-threshold multiplier (1.0/0.85/0.7); and one real capability gate — NORMAL never builds the multi-phase plan at all (2342-2344), so the default difficulty players face has no charge intents, no lock targets, no shooting lanes. Six of the thirteen advertised difficulty capabilities are dead config.

## Implications

Three load-bearing implications for the feasibility verdict. (1) The architecture explains the empirical null results better than 'heuristics are hopeless': target-selection micro-corrections measured zero because target choice is dominated by macro terms the corrections never touch, and movement quality is capped not by scoring accuracy but by the fact that destinations are constructed singly and never compared — the cheapest structural upgrade with headroom to pay for it (8-40x compute at 1-5s/decision) is K-candidate destination enumeration scored by the existing evaluators, which requires no engine refactor at all. (2) Rollout/search-based play is NOT reachable by flipping a switch: the 'Competitive look-ahead' difficulty is fiction, and a real one-ply-with-opponent-reply search needs either a pure step kernel extracted from ~37k lines of phase Nodes or fragile save/patch/restore around a live singleton with ~20 wired signals — a large refactor whose payoff is unproven, though RulesEngine's already-pure combat resolution means damage-reply estimation (not full game rollout) is a realistic middle path. (3) The user's proposed mitigations fit the architecture cleanly: scripted deployment plans would replace the weakest, most consequence-laden formula in the system (deployment is deterministic and order-blind today), and pre-authored mission/board game plans would slot into the existing plan-dictionary layer (_turn_movement_plan / phase_plan) that already exists as the coordination mechanism — both are low-refactor, and both attack exactly the layers (deployment, macro assignment) where the one large measured win (reserves cap, 12→39 VP) already came from. The discouraging corollary: everything measured so far says wins come from strategic-layer structure, not tactical accuracy, and the strategic layer is authored logic — meaning improvement is bounded by authoring effort and the lab's ~hundreds-of-games-per-hypothesis measurement cost, not by any quick algorithmic unlock.
