A harness for improving the AI — and the gap where the learning still isn’t

The AI already explains every decision it makes. Until now it threw all of that away the instant the process exited. This is what got built, what it can actually change, and—more usefully—what it still can’t.

Q1

What can it change?

Exactly two surfaces, both inside AIDecisionMaker.gd. Neither touches the ~22,300 lines of decision logic — only the numbers that logic consults.

104tunable parameters
96 float · 8 int
166call sites reading them
13rule condition types
3rule action operations
9context keys rules can test

The tunable surface is smaller than the constant count suggests

The file declares 152 constants, but only the 104 actually read through get_param() / get_param_int() can be reached from a profile. Writing the other 48 into a profile produces a candidate that validates, runs, and changes nothing — burning a full evaluation budget to measure zero. params_manifest.py derives the real list from source rather than trusting a hand-kept note.

What it cannot change

  • The features the heuristic scores on. New terms are code, not configuration — parameter search cannot invent them.
  • Anything about phase order, rules resolution, or engine behaviour.
  • The 7 of 17 AIDifficultyConfig gates that have no callers at all.
Q2

How does it change them?

Through a profile: a JSON file with a flat parameters map and a rules array. Rules carry AND-ed conditions and actions (override / multiply / add). At read time a parameter resolves in a fixed priority order:

PrioritySourceSet by
1 — highestrule overridea profile rule whose conditions currently hold
2player profilethe parameters map, per player
3global configai_config.json
4 — fallbackconst defaultthe source declaration

Learning is offline, and deliberately so

Search happens on the box; players receive a static, version-stamped, human-reviewed profile. Three reasons. Every accepted change clears the scenario suite and a two-matchup grid before anyone sees it — online adaptation cannot be gated that way. The AI narrates its reasoning in the game log, and a fixed profile keeps that narration truthful. And a player might play 20 games a month against measurement noise of ±9–15 VP, so online adaptation would be fitting dice, not skill.

Four ways the engine changes nothing, silently engine behaviour

ProfileManager.validate_profile() checks structure only — format tag, version, name, rules having ids. A generated profile can pass it and do nothing, or the opposite of what it says. validate_profile.py now blocks all four; the engine still behaves this way.

silent zero
Multiplying an undeclared parameter switches it off. _get_base_param_value returns 0.0 for any parameter not in the profile or ai_config.json — including every parameter whose only value is a const. So “multiply WEIGHT_CONTESTED_OBJ by 1.2” does not scale 8.0 to 9.6; it computes 0.0 × 1.2. add is the same trap quieter: it yields the bare addend.
passes
An unknown condition type is treated as met. _check_rule_conditions is a match with no default arm, so a misspelling doesn’t fail the rule — it fires the rule unconditionally, every round. round_gt is not a type; round_gte is.
dropped
An unknown action operation vanishes. Anything that isn’t override/multiply/add matches no arm and is discarded without warning.
dead
Every vp_* condition is inert. _get_vp_diff reads meta.player1_vp/player2_vp; a repo-wide search shows those keys are written by exactly one test. Real VP lives at GameState.state.players[pk].vp. So vp_diff is always 0: vp_ahead and vp_diff_gte never fire, and vp_behind and vp_diff_lte fire always.
Q3

How does it identify what to change?

This is what M1 unlocked. AIDecisionMaker already built a complete “here were my options, here is how I scored each one, here is what I picked, here are the parameters I used” trace for every decision — and discarded all of it at process exit. The outcome went to a separate file that had no idea the decisions existed. Nothing joined them, so nothing could learn from them.

Now every game leaves one self-describing record, and a season becomes four SQL views.

ViewWhat it answers
decision_outcomes Every decision joined to how its game ended. This is the join that did not exist before.
round_vp Per-round VP deltas — an intermediate reward signal, so credit assignment doesn’t depend on one terminal number across 400–600 actions.
arm_summary Margin and spread per fixture, arm and commit. Refuses to pool across commits by default.
data_quality Games that dropped decision batches or recorded none — a biased sample, flagged rather than averaged in.

The mining signal: regret against the AI’s own opinion

Each decision row carries the gap between the candidate the AI took and the best score it assigned to any candidate. Nonzero means something — difficulty noise, or a coordination override — deflected the choice away from the heuristic’s own judgement. It measures deviation from the heuristic, not from truth, so it points at questions rather than answering them.

The first indexed games already raise one. Movement departs from its top-scored candidate in 217 of 332 decisions, mean gap ~7.9 score units — an order of magnitude beyond what Hard’s ±0.5 noise can produce, so something structural is overriding the score. Shooting, charge and fight barely deflect at all. The cause has not been traced. That is precisely the kind of question the dataset exists to make askable.

Before any of this counts: the environment gate M0

Every AI baseline predating this work was tuned on a fixture carrying an army-list header row imported as a unit — points: 2000, keywords: ["UNKNOWN"]. It inflated one army from 1,840 to 3,840 points, doubled the Strategic Reserves cap, and drew the enemy AI into shooting a 1-wound phantom. Nothing recorded which fixture a result came from, so the corruption stayed invisible and invalidated every historical tuning decision at once. fixture_check.py now fails that fixture and passes the two mirrors, and every game record pins the fixture’s SHA-256 alongside the commit.

Q4

What are its limitations?

The binding one is not subtle, and it is not the algorithm.

Measurement, not ideas, is the bottleneck

Paired effect standard deviation is 8.37 VP. Detecting an effect of size Δ at two standard errors needs (2 × 8.37 / Δ)² pairs:

Effect to resolvePairsGames per matchupWall clock @ 3 lanes
5 VP1224~50 min
4 VP1836~1.2 h
3 VP3264~2.1 h
2 VP71142~4.7 h

The project already ran the natural experiment. Mining 1,029 match transcripts produced 31 evidence-backed findings; six were implemented; the measured result was −2.05 VP, 95% CI [−7.2, +3.1] — indistinguishable from zero, point estimate mildly favouring the old behaviour. The ideas weren’t obviously bad. They were unjudgeable, because at this noise level idea quality cannot be assessed without an evaluator. That is why the evaluator came first.

throughput
~6 minutes per game. Measured 350–403 s. Roughly 350–500 games/day at three lanes on four cores — the whole budget, for everything.
variance
Games are not seed-reproducible. Score noise runs through a bare unseeded randf(), including inside a movement-ordering sort comparator, so activation order itself is stochastic. Fixing it enables common-random-number pairing and single-rollout counterfactuals. Not yet done.
coverage
The trace is shallower than it looks. Only four decision sites emit records — movement, shooting, charge, fight. Command, scoring and reactive decisions are invisible. Shooting records the plan rather than the alternatives considered, and the “hold fire to stay Hidden” branch returns before its record is written.
proxy
VP margin is a proxy, and proxies get gamed. A search optimising it may find degenerate play or exploit engine bugs. The AI also has to look like it is playing 40k, which no single number captures.
locality
Two mirror fixtures is a narrow world. Mirrors remove army asymmetry by construction, which is what makes an A/A test meaningful — but a weight that wins an Ork mirror need not transfer, and evaluation runs at difficulties players may not use.
not built
Nothing searches yet. No sensitivity screen, no optimiser, no automated accept/reject. Today a person reads arm_summary and edits a profile. The harness shortens that loop; it does not close it.
Q5

How could it be improved?

In this order, because each stage is worthless without the one before it. Every stage carries a kill criterion, so the effort is falsifiable rather than open-ended.

NextWhat it addsCostKill criterion
Seed the AI’s RNG Exact same-seed replay; common-random-number pairing cuts the games needed per comparison; single-rollout counterfactuals become possible. ≤ 2 days If same-seed games aren’t identical after two days, ship the paired driver without it and move on.
Paired A/B driver Seed-paired, side-swapped arms with sequential stopping and an always-on A/A arm that halts the campaign if the harness drifts. 1–3 days — foundational
Sensitivity screen One-at-a-time ±30% over ~15 candidate weights, to find which constants actually move the margin. ~300 games If fewer than five parameters move it by ≥2 VP, drop the optimiser for plain coordinate descent.
Automated search Cross-entropy method over the surviving 10–15 weights, with racing to kill bad candidates early. First unattended accept/reject. 1.5–3.5k games No accepted ≥4 VP change within one 30-day season → stop tuning weights, move the budget to feature work.
Widen the trace Fix the dead vp_diff context; instrument command, scoring and reactive decisions; add per-phase board digests. — — unlocks rule search
Rule-DSL search Search over readable rules rather than bare numbers. The one place an LLM plausibly beats its cheap baseline — proposing semantically sensible rules random mutation would take thousands of games to stumble on. — Dies if its accept-rate per 1k games doesn’t beat templated mutation.

The bar for calling any of it a success

Within one 30-day season and ≤12,000 games, the automated cycle must produce a profile change that beats the shipped default by ≥ +4 VP/game pooled across both mirrors at ≥2 standard errors, with no matchup worse than −2 VP, no increase in stall rate, zero new scenario-suite failures, and a concurrent A/A arm that stays within 2 se of zero. If nothing clears that bar inside the season, weight tuning is falsified at this budget and gets stopped — and the dataset remains valuable regardless.
